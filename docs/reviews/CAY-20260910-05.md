## Findings

All source line numbers refer to the target head, not the review test files.

### F1 — P1: The maximum-spend guard does not bound spending

Location: `evals/providers/openrouter-config.ts:121–139`, `evals/providers/openrouter.ts:292–304`.

`noteRequest()` only increments a counter. Cost is checked after a response and only when it exceeds the cap. With a $0.01 cap and mocked responses costing $0.01, two scenario calls make two requests and spend $0.02. Even below the cap there is no reservation for the next request, input-token bound, or verified price ceiling. A timeout/network retry may already have been billed; a timeout followed by success reports only the successful request's $0.01 and one usage request, with no uncertain-cost state.

Required correction: reserve a conservative request/attempt cost before dispatch using the approved configuration, or enforce a verified provider-side budget that covers this run. Refuse requests with exhausted or insufficient remaining budget. Preserve every attempt and treat uncertain charges as unknown until reconciled; retries must not silently restore a fully measured cost. Do not describe the current threshold as a hard spending cap.

Reproductions: the two `F1` tests in `tests/cay-review-adversarial.test.ts`.

### F2 — P1: The paid-execution gate protects only the CLI

Location: `evals/providers/openrouter.ts:106–110` (default HTTP transport); constructor/run at `:168–196`.

The exported provider's default transport never calls `assertPaidExecutionAllowed`. With `CI=true`, no `CANAIYET_PAID_RUN`, and a synthetic key, constructing `OpenRouterProvider` without an injected client reaches `fetch`. The review intercepts that call; no request reaches OpenRouter. The new CLI correctly refuses this environment, and the existing tests use mocks, but the reusable provider does not enforce the promised boundary and can also run with an uncapped ledger.

Required correction: enforce authorization and valid budget configuration at the real-network boundary, while retaining an explicitly mocked path for tests. Test the default transport, not just the separate guard function.

Reproduction: `F2` in `tests/cay-review-adversarial.test.ts`.

### F3 — P1: Failed or truncated responses can produce a valid passing result

Location: `evals/providers/openrouter.ts:65–91,234–235`.

The parser discards `finish_reason` and choice-level errors. Any object-valued message without tool calls ends the loop successfully, even `{}`. For frozen LEAD-012, a tool response sends the correct $180 reply, then a final response with `length`, `error`, or `content_filter` produces `success: true` and `benchmarkInvalid: false`. A malformed empty message with an error also finishes without invalidation. This is not merely a displayed diagnostic score on an explicitly invalid run: the normal persistence path marks these runs completed.

Required correction: validate the response envelope, tool-call structure, and terminal reason; require a recognized successful terminal state. Preserve failures and stop invalid execution before it can become a completed benchmark. Malformed argument JSON currently produces a tool error without mutation, which is a useful control to retain.

OpenRouter documents these terminal reasons and choice-level errors in its [API reference](https://openrouter.ai/docs/api_reference/overview). Reproductions: four `F3` cases in `tests/cay-review-adversarial.test.ts`.

### F4 — P1: Served provenance is discarded before artifacts and persistence

Location: `evals/runners/run-suite.ts:58–69`, `evals/persistence/persist-run.ts:84–90`.

The provider collects requested/served model, route/provider, generation IDs, and request counts, but `runScenario` copies only token/cost totals. Neither the serialized suite nor persistence payload contains the mocked generation ID or served provider. The tool configuration stores the requested model and validity flags only; it omits actual route, execution caps, prompt/configuration identity, and per-attempt accounting. Even within the provider, served-provider values are overwritten each turn. The runbook's request to inspect served provenance cannot be fulfilled from the artifact.

Required correction: carry per-request provenance and the frozen execution configuration through scenario, suite, local artifact, and durable rows. Preserve provider changes rather than keeping only the last value. Retain enough private tool/state evidence to independently replay the judge: the existing `actualState` projection also omits contacts, notes, deals, and appointments, and reduces tasks to titles. Those omissions predate this PR, but the new persistence path inherits them.

Reproduction: `F4` in `tests/cay-review-adversarial.test.ts`. This test uses synthetic metadata; it makes no claim that a real provider served a model.

### F5 — P1: Partial persistence leaves a completed run that acceptance permits

Location: `evals/persistence/persist-run.ts:141–146,159–164`, `scripts/publish-results.ts:45–57`.

The writer inserts a run with `status: completed` before inserting results. A failed result insert leaves a completed run with no results. `decideAccept` permits it; the actual acceptance script reads no results, expected scenario count, provenance, or independent verification record before publishing. Therefore a persistence error can later become accepted evidence.

Required correction: write the run/results atomically or leave the run non-completed until all unique expected results are durable. Acceptance must independently validate completeness, validity, counts, scenario membership, provenance, and the review decision. Preserve failed attempts explicitly, and define retry/idempotency behavior.

Reproduction: `F5` in `tests/cay-review-adversarial.test.ts`, using a result writer that throws after the run insert.

### F6 — P1: The public reader considers missing or contradictory results complete

Location: `evals/evidence/pair.ts:120–135`; `lib/data/public-data.ts:191–216` supplies `[]` when no result rows exist.

`chainComplete` checks array truthiness, so zero or one result satisfies a claimed 12-scenario run. The reader also accepts a 12/12 headline with twelve failing result rows. It computes the headline from run counters without reconciling them with the details. A non-null pointer and `published` flag do not prove completeness, ownership, validity, or acceptance. This compounds F5 and also occurs when RLS hides results or a nested scenario row is unavailable.

Required correction: validate exact unique result membership and counts, capability/run ownership, completed and valid acceptance state, and recomputed successes/critical failures. Fail closed to an internally consistent fallback or unavailable-evidence state if any check fails. Include run-derived configuration/evidence classification where necessary rather than stale capability metadata.

Reproductions: three `F6` cases in `tests/cay-review-adversarial.test.ts`. The ordinary missing-run fallback does keep the local headline and local details together; that narrower guarantee passes.

### F7 — P1: Acceptance is neither atomic nor concurrency-safe

Location: `scripts/publish-results.ts:48–60`.

Two concurrent acceptances read the same null pointer, both pass the replacement check, and both update by capability ID alone. The second silently replaces the first without `--replace-accepted`. Separately, publishing the run succeeds before the pointer write; if that second write fails, the unaccepted run remains public under the existing `runs_public_read` / `results_public_read` policies. The real acceptance script was exercised against an in-memory Supabase double for both cases.

Required correction: perform acceptance in one database transaction with a row lock or compare-and-set on the expected prior pointer, include all evidence checks, record reviewer/acceptance metadata, and publish only on successful commit. Ensure repeated acceptance is explicitly idempotent. Anonymous callers must not gain an acceptance RPC.

Reproductions: both `F7` tests in `tests/cay-review-acceptance.test.ts`.

### F8 — P2: New runs can rewrite scenario definitions used by accepted history

Location: `scripts/run-openrouter-cap001.ts:85–100`; schema uniqueness at `supabase/migrations/20260910213000_init.sql` on `(capability_id, slug)`.

Scenario upsert replaces the fixture version, expected/forbidden state, title, and payload under an existing scenario ID. A later intentional run using the same slug and a revised fixture therefore changes the definition referenced by an older accepted result, before the new run is accepted. The public reader joins that mutable scenario row for its title. The current fixtures are unchanged; this finding concerns the new writer's behavior when the suite evolves.

Required correction: make run-referenced scenario definitions immutable, keyed by version/content identity, or snapshot the full definition per run and reject conflicting overwrites. Re-persisting the identical definition can be idempotent. Verify that an unaccepted run cannot alter the meaning of an accepted run's details. This finding is established by code/schema inspection, not a live database write.
