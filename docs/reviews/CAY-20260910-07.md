## Blocking findings

Locations below refer to the exact target head. R1–R7 are the remaining/new findings for this review, not replacements for the historical F identifiers.

### R1 — P1: Reservation does not establish a spending ceiling

`evals/providers/openrouter-config.ts:136–150`; `scripts/run-openrouter-cap001.ts:27`.

The CLI constructs `SpendLedger(config.maxSpendUsd)` without a per-request reserve. `beginAttempt` uses `reserve = remaining`, compares remaining to itself, and increments a counter; it neither holds a monetary reservation nor bounds the charge of the request. There is no verified price/configuration ceiling or provider-side budget enforcement. A $0.01 ledger immediately permits dispatch with no known upper request cost. `sameRequestRetry` also bypasses the uncertain-charge stop: two mocked timeout attempts are sent despite the first charge being unknown.

The builder's acknowledged overshoot limitation remains material: invalidating a result after a high bill does not enforce the human's dollar approval. It is broader than a final response lacking price metadata, and defaults allow potentially billed retries. The runbook asks for a “Request reserve USD,” but no environment/CLI setting supplies it.

Required correction: enforce a verified conservative per-attempt cost bound, or a verified provider-side limit covering the run; refuse dispatch without sufficient reserved budget. Reconcile or stop on unknown charges before retrying. Wire the approved reserve into the command or replace the misleading reservation workflow. Retain the now-correct exhausted-cap and unknown-cost behavior.

Evidence: two `R1` contracts in `tests/cay07-new-contracts.test.ts`.

### R2 — P1: Real transport is allowed in tests and accepts an infinite cap

`evals/providers/openrouter-config.ts:56–69`; `evals/providers/openrouter.ts:137–154`.

The correction removed the original `NODE_ENV === "test"` block. With test mode, a leftover paid flag, and a positive cap, the real transport reaches intercepted fetch. Separately, `OPENROUTER_MAX_SPEND_USD=Infinity` passes `Number(value) > 0` and `assertPaidExecutionAllowed`, also reaching fetch. The CLI's parser rejects infinity, but the transport bypasses that parser. All credentials and HTTP responses in the reproduction are synthetic.

Required correction: restore test-environment refusal at the real transport, retain injectable mocks, and enforce finite bounded configuration at every real-network entry point. Validate token/timeout limits and fallback constraints there as well. No-human-flag, CI, and Vercel checks must remain effective.

Evidence: two `R2` contracts in `tests/cay07-new-contracts.test.ts`.

### R3 — P1: Malformed tool calls are repaired or discarded into a valid pass

`evals/providers/openrouter.ts:78–92`.

The parser invents missing IDs, overwrites any tool-call type with `function`, substitutes non-string arguments, and filters nameless calls out. Frozen LEAD-012 still produces `success: true, benchmarkInvalid: false` for a correct send operation with a missing ID, unsupported call type, or a malformed nameless sibling call. The terminal-reason correction does not validate the rest of the envelope.

Required correction: validate each call's ID, type, name, argument shape, and uniqueness before applying any call in that response. Preserve malformed-envelope/tool errors and fail closed; do not silently repair or omit them. Invalid JSON must continue to avoid World mutation.

Evidence: three `R3` contracts. Expected states and judge remain untouched.

### R4 — P1: Retry history/configuration remains unauditable, and CLI aggregation is missing

`evals/providers/openrouter.ts:359–379`; `scripts/run-openrouter-cap001.ts:39–63`; `evals/persistence/persist-run.ts:84–96`.

Attempt records are created only in `account()` for a parsed response. A timeout followed by a response records one attempt and one request, not two; exhausted transport failures can have no attempt history. Setting total cost null is an improvement, but it does not preserve what happened. The actual CLI also constructs its own suite rather than using the corrected summarizer, leaving `suite.provenance` absent. In an offline invocation of that CLI, per-scenario generation ID is present while `run.toolConfiguration.generationIds` is empty. Successful per-scenario provenance is retained in `actual_state`; it is not wholly lost as it was in the first version.

Neither path freezes the executed token/turn/retry/timeout/spend configuration or prompt/tool configuration identity. A git SHA alone cannot recover environment-supplied settings. The World projection still omits contacts used in CAP-001 judging.

Required correction: create a durable attempt record before each dispatch and complete it with response/error/uncertainty data; preserve all attempts and counts. Freeze configuration and prompt/tool identity. Use one summarizer for the production CLI and generic runner, and ensure private audit state covers every judged field.

Evidence: `R4` retry contract and `tests/cay07-cli-contract.test.ts`. The latter executes the actual CLI with fetch and artifact writes mocked; it is not a paid smoke test and writes no benchmark artifact.

### R5 — P1: Persistence and the actual acceptance RPC validate counts, not exam membership

`evals/persistence/persist-run.ts:178–183`; `supabase/migrations/20260911043000_accept_benchmark_run.sql:42–46`.

Settlement only compares array length with scenario length. A suite containing twelve copies of one result can become completed. The production CLI calls the SQL RPC, not `acceptRunAtomic` / `validateAccept`; the SQL checks `count(*) = total_count` but not distinct expected scenario IDs, scenario ownership, or outcome totals.

Executing the repository SQL in isolated PostgreSQL 18.3/PGlite reproduced all three outcomes: two copies of one scenario were accepted as two scenarios; a result referencing another capability's scenario was accepted; a 1/1-success run with a failing result was published. These are actual SQL outcomes, not a JavaScript model of the SQL. Existing RLS exposes published rows, so public-reader fallback alone does not contain the problem.

Required correction: freeze the intended scenario/version membership on the run; require exactly those results once, matching capability ownership, validity and recomputed success/failure/critical totals before settlement and transactionally before acceptance. Enforce duplicate protection in the database and define retry/idempotency behavior. Verify the actual RPC instead of an unused helper.

Evidence: `R5` TypeScript contract and the three `DEFECT REPRODUCED` entries in `CAY-20260910-07-sql-results.json`.

### R6 — P1: Public loader never supplies the fields used by the new safety checks

`lib/data/public-data.ts:136–152`; `evals/evidence/pair.ts:126–128`.

`toRun` drops `status`, `tool_configuration.benchmarkValid`, and `capability_id`. Pairing makes its corresponding checks conditional on optional fields, so all three checks are skipped for real database responses. Exercising the actual Supabase client/public loader with HTTP doubles shows accepted-run headlines for a failed run, explicitly invalid run, and another capability's run when result counts match. The schema's accepted-run foreign key does not enforce matching capability ownership.

Required correction: carry required run/capability identity and explicit completed/valid/accepted state from database rows into the reader; validate them unconditionally. Include expected result identity/snapshot checks, rather than trusting matching counts alone. Test `getPublishedPage` and the row mapping, not only `pairEvidence` with manually enriched objects.

Evidence: three `R6` loader contracts in `tests/cay07-new-contracts.test.ts`.

### R7 — P2: Versioned scenario repersistence is not idempotent

`evals/persistence/scenario-identity.ts:11–23,38–42`; `scripts/run-openrouter-cap001.ts:88–100`.

The writer hashes the slug as part of the definition. After a changed definition is inserted with `base__hash`, the next read rehashes that versioned slug, while incoming identical content still uses `base`. The hashes cannot match, so it attempts to insert the already existing versioned slug again and encounters the unique constraint. The hash also uses ordinary JSON serialization, so semantically identical JSONB objects with different key ordering produce different identities.

Required correction: distinguish stable scenario identity from storage slug, persist/verify a canonical content hash, and canonicalize object keys recursively while preserving array order. Reuse identical definitions after a database round trip and handle concurrent identical inserts without overwriting history.

Evidence: two `R7` identity contracts. Original definitions are no longer overwritten; that part of F8 is corrected.
